# TECHNICAL_ARCHITECTURE — WHYTHEWEAKEST OS

## 1. Решение по стеку

Новый репозиторий, стек как в `deadlock-cb` владельца, чтобы переносить проверенные модули и не учить новое:

| Слой | Выбор | Почему |
|---|---|---|
| Язык | TypeScript (Node.js 22 LTS) | Один язык для бота, worker и Dashboard |
| Web | Next.js 15 (App Router), React 19, Tailwind CSS | Уже освоен владельцем, серверные действия удобны для одного пользователя |
| БД | Prisma 6 + SQLite (режим WAL) | Разрешено ТЗ для MVP, ноль инфраструктуры, файл легко бэкапить. Переход на PostgreSQL сменой провайдера (раздел 9) |
| Telegram | grammY | Типизированный, живой, поддерживает и long polling, и webhook |
| AI | Локальная открытая модель через Ollama на ПК владельца (решение 09.11.2026), интерфейс `AiProvider`. Claude API только как необязательный запасной провайдер, выключен по умолчанию | Нет расходов на токены, работает офлайн. Провайдер заменяемый |
| Транскрибация | Интерфейс `Transcriber`: облачный Whisper-совместимый API или локальная модель | Claude не принимает аудио. Выбор за владельцем |
| Извлечение ссылок | `fetch` с лимитами + `@mozilla/readability` + Open Graph / oEmbed | Без браузерной автоматизации и обхода защит |
| Изображения | `sharp` | Удаление EXIF, превью |
| Валидация | zod | Окружение, вход API, ответы AI |
| Логи | pino с маскировкой секретов | Перенос из `deadlock-cb` |
| Тесты | Vitest (unit, integration), Playwright (e2e) | Как в `deadlock-cb` |

Redis, очереди-брокеры, Kubernetes, отдельный бэкенд-сервис не нужны.

Три процесса из одного репозитория: `web`, `bot`, `worker`. Бизнес-логика только в `src/core`; интерфейсы (Next.js, grammY) вызывают сервисы и ничего не решают сами. Бот и worker можно запустить одним процессом на слабой машине (флаг `--with-worker`).

## 4. Ключевые потоки

### 4.1. Приём материала из бота

1. Бот получает обновление и проверяет `from.id` по allowlist. Чужие обновления не обрабатываются.
2. В одной транзакции: запись `telegram_updates` с уникальным `update_id` (повтор доставки от Telegram отбрасывается), создание `materials` в статусе `inbox`, задачи в `jobs`.
3. Для ссылок вычисляется нормализованный URL (нижний регистр хоста, без `utm_*`, `fbclid`, якоря, завершающего слеша) и его sha256. Уникальный индекс не даёт создать дубликат; бот отвечает «Уже есть».
4. Бот отвечает «Сохранено» сразу после коммита. AI и сеть в этом шаге не участвуют, поэтому материал не теряется при их сбое.
5. Worker выполняет задачи: скачать файл из Telegram (до 20 МБ), извлечь содержимое ссылки, классифицировать (Curator). Каждая с повторами при временных ошибках.

### 4.2. Публикация

```
approved / scheduled(time<=now)
        │  claim: UPDATE posts SET status='publishing', publish_attempt_id=?
        │         WHERE id=? AND status IN ('approved','scheduled') AND approval_valid
        ▼
   publishing ──sendMessage / sendPhoto / sendMediaGroup──►
        │
        ├─ ответ OK ─────────────► published  (сохранить message_id, ссылку)
        ├─ 429 retry_after ───────► вернуть в прежний статус, повтор после паузы
        │                           (Telegram явно сообщает, что не отправил)
        ├─ 400/403 однозначный ───► failed (уведомить автора)
        └─ таймаут / обрыв сети ──► publish_unknown (уведомить, НЕ повторять)
```

- Захват поста это один условный UPDATE: второй worker или повторный клик ничего не захватит.
- Перед отправкой проверяется действующее подтверждение: запись `approvals` с хешем, совпадающим с текущим содержимым.
- `publish_unknown` разрешает автор: «Пост вышел» (вводит ссылку или система находит его) или «Не вышел, отправить снова» (это новое подтверждение).
- В тестах и до отдельного разрешения владельца `PUBLISH_TARGET` указывает на тестовый канал. Основной канал включается только явной настройкой и требует подтверждения в Settings.

### 4.3. AI

- `AiProvider.complete({ mode, promptVersion, input, schema })`; ответ валидируется zod. Невалидный ответ это ошибка генерации, а не мусор в БД.
- Провайдер по умолчанию: Ollama (`OLLAMA_URL`, модель по `.env`, выбор под видеокарту ПК). Кандидаты с хорошим русским: Qwen, T-lite, Vikhr. Claude API включается только вручную.
- Стиль: перед генерацией черновика из базы постов канала-образца подбираются 5–10 самых похожих постов (локальные эмбеддинги) и подаются модели как примеры. Дообучение (LoRA) только если постов-образцов окажется много и качества не хватит.
- Категории: сначала маленький классический классификатор (TF-IDF + логистическая регрессия), обученный на постах образца; LLM подключается, если уверенность низкая.
- Таймаут, 2 повтора на временные ошибки, затем задача `failed`, материал остаётся в `inbox` с пометкой «AI недоступен», ручная работа не блокируется.
- Промпты лежат в `src/core/ai/prompts/` с версией; версия пишется в `ai_generations`.
- В промпт не передаются имя владельца, токены, настройки.

### 4.4. Извлечение ссылок (Этап 2, в MVP только Open Graph)

- Только `http`/`https`, запрет приватных и локальных адресов после DNS-резолва (защита от SSRF), лимит ответа 5 МБ, таймаут 10 с, не более 5 редиректов.
- Учитывается `robots.txt`; при запрете сохраняется только ссылка и то, что прислал автор.
- Страницы за авторизацией, CAPTCHA, paywall не обходятся.

## 5. Авторизация

- **Бот:** allowlist Telegram ID (`OWNER_TELEGRAM_IDS` в `.env` + таблица `users` для администраторов). Проверка на каждом обновлении и каждом callback.
- **Dashboard:** вход по одноразовой ссылке из бота (`/login` → ссылка на 5 минут, одноразовая, привязана к Telegram ID). Работает на iPhone без настройки домена в BotFather. Опционально Telegram Login Widget, если у Dashboard будет постоянный домен.
- Сессии в БД, cookie `httpOnly`, `Secure`, `SameSite=Lax`, CSRF-токен для изменяющих действий, rate-limit на вход.
- Роли MVP: `owner` (всё, включая подтверждение публикации), `admin` (всё, кроме управления доступом и секретами; право подтверждать публикации выдаётся владельцем явно).

## 6. Хранение файлов

- Файлы в `storage/` по sha256 (`storage/ab/cd/abcd…`), в БД только метаданные. Одинаковые файлы хранятся один раз.
- Проверка типа по magic bytes, лимиты размера.
- EXIF и GPS удаляются при подготовке к публикации; оригинал хранится, пока владелец не удалит.
- Удаление материала: мягкое → окончательное с удалением файлов, если на них больше никто не ссылается.

## 7. Надёжность

| Требование ТЗ | Реализация |
|---|---|
| Идемпотентность | Уникальные `update_id`, хеш URL, sha256 файлов, условный захват поста, ключи дедупликации задач |
| Защита от повторной обработки | Задача с `dedup_key`, статусами и арендой; результат пишется в одной транзакции со сменой статуса |
| Повторы при временных ошибках | Экспоненциальная задержка 1, 2, 4… мин, максимум попыток по типу задачи. Публикация: см. 4.2 |
| Журнал событий | `activity_logs` (только добавление) + pino в файл с ротацией |
| Ошибки Telegram API | Разбор `error_code`, `retry_after`; глобальный лимитер исходящих запросов |
| Резервное копирование | Worker раз в сутки: онлайн-бэкап SQLite (`VACUUM INTO`) + архив `storage/`, хранение 14 копий; `npm run restore` |
| Восстановление после перезапуска | Задачи с просроченной арендой возвращаются в очередь; посты в `publishing` с истёкшей арендой переходят в `publish_unknown`, а не в повтор |
| Проверка внешних сервисов | `/api/health`: БД, диск, `getMe` бота, ping AI, транскрибация; heartbeat worker и бота. Видно на Overview |

## 8. Безопасность

- Секреты только в `.env` (в `.gitignore`), `.env.example` без значений. Проверка схемой при старте.
- Логгер маскирует токены, включая URL `api.telegram.org/bot<token>/`.
- Секрет-сканер (gitleaks) в CI и pre-commit.
- Настройки в Dashboard никогда не возвращают секрет целиком.
- Dashboard не индексируется (`noindex`, `robots.txt`), заголовки безопасности (CSP, frame-ancestors).
- В БД не хранятся IP в открытом виде (HMAC, как в `deadlock-cb`).

## 9. Переход на PostgreSQL

- Схема пишется переносимо: статусы строками с проверкой zod, JSON как текст с валидацией, без сырого SQL, специфичного для SQLite.
- Переход: смена `provider`, новая базовая миграция для PostgreSQL (история миграций Prisma привязана к провайдеру), скрипт переноса данных по таблицам, проверка счётчиков. Очередь задач на PostgreSQL получает `FOR UPDATE SKIP LOCKED` из `deadlock-cb`.
- Когда переходить: несколько worker-процессов, хостинг без постоянного диска, полнотекстовый поиск с морфологией (Этап 3).

## 10. Развёртывание

Вариант выбирает владелец (вопрос в IMPLEMENTATION_ROADMAP.md). Без отдельного разрешения ничего не разворачивается.

| | A. Домашний ПК (Windows 11) | B. Небольшой VPS |
|---|---|---|
| Запуск | Node.js или Docker Desktop | Docker Compose + Caddy (HTTPS) |
| Бот | long polling, публичный адрес не нужен | long polling или webhook |
| Dashboard с iPhone | через Tailscale | по домену с HTTPS |
| Работает, когда ПК выключен | нет: материалы ждут в Telegram до 24 часов, запланированные посты не выйдут | да |
| Стоимость | 0 | порядка нескольких сотен рублей в месяц |

## 11. Тестирование

- Unit: машина состояний, нормализация URL, проверки черновика, лимиты Telegram, разбор ошибок.
- Integration: временная SQLite на каждый прогон, фейковый Telegram Bot API (локальный HTTP-сервер), подменённый `AiProvider`. Реальные сервисы в автотестах не вызываются.
- e2e: Playwright по сценариям A и B, включая мобильный вьюпорт iPhone.
- Ручная приёмка: тестовый бот и тестовый канал владельца.
- CI: GitHub Actions, lint, typecheck, unit, integration, e2e, gitleaks.
